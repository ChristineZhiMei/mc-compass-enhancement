# 方案反驳验证文档

## 1. 反驳点分析

| # | 反驳点 | 可能出错的原因 | 验证方法 |
|---|---|---|---|
| 1 | 修改一个常量是否真能完整开放 256 | Payload 或服务端可能有隐藏上限 | 追踪 Codec、Payload 编码、保存与扫描再校验 |
| 2 | “搜索过”是否能等于服务端已执行 | 客户端发包可能被冷却或校验拒绝 | 检查现有 C2S/S2C 协议与冷却逻辑 |
| 3 | 历史能否直接在配置页当前布局中加一行 | 小尺寸 GUI 可能溢出 | 核对当前面板高度与所有 Y 偏移 |
| 4 | 上/中/下能否用 Lodestone 坐标计算 | 坐标取整可能改变 ±2 边界 | 对比 `Vec3d` 命中坐标与 `BlockPos.ofFloored` |
| 5 | 256 格是否能延用当前同步算法而无代价 | 线性尺寸翻倍会显著扩大候选体积 | 统计区块列、section 与方块访问上界 |

## 2. 反驳执行

### 2.1 范围上限的单一真实源

**假设**：仅修改 `MAX_RADIUS` 会遗漏其他 128 上限。

**证据**：`Codec.intRange`、`RadiusSlider`、`ModNetworking.handleSave`与 `isValid` 均引用该常量；`SaveCompassConfigPayload` 使用 `VAR_INT`，没有独立 128 限制。

**反驳结果**：失败。原方案成立。

### 2.2 历史语义

**假设**：客户端发包后记录可以精确表示“服务端已搜索”。

**证据**：扫描协议是无响应 C2S Payload；服务端可在主手、配置或 10 tick 冷却校验处提前返回。

**反驳结果**：成功。历史准确语义修正为“客户端已尝试发起搜索”。若产品未来要求仅记录真正执行或成功命中，必须新增 S2C 确认。

### 2.3 GUI 高度

**假设**：保持现有 210px 面板并将后续控件整体下移即可。

**证据**：当前最后一行按钮位于 `top + 188`，面板已接近 210px；屏幕高为 240px 时 `top` 仅 15px。

**反驳结果**：成功。需引入统一布局常量，将历史做成紧凑 20px 横向行，重新排列标签、控件、警告与底部按钮。

### 2.4 垂直方向数据源

**假设**：可用 `BlockPos.ofFloored(nearest.target())` 后的 Y 计算方向。

**证据**：方块/容器命中坐标为中心点，掉落物为实时小数坐标；取整会在 ±2 阈值附近造成分类偏差。

**反驳结果**：成功。必须先用 `nearest.target().y - player.getY()` 分类，再为 Lodestone 取整。

### 2.5 256 格性能

**假设**：冷却和 palette 否决足以保证 256 格扫描不会卡服务器 tick。

**证据**：256 格包围盒最多横跨 33×33 个区块列。对 palette 中广泛存在的目标，最坏可达约 1.07 亿次方块状态读取；10 tick 冷却只限制请求频率，不能缩短单次主线程扫描。

**反驳结果**：成功。本轮依需求提供 256 上限，但不宣称它在所有目标上都无性能代价；后续优先实施近到远剪枝和跨 tick 分片。

## 3. 最终方案

### 方案变更

| # | 原方案 | 修正后方案 | 原因 |
|---|---|---|---|
| 1 | 历史表示搜索过 | 历史表示客户端已尝试发起搜索 | 无 S2C 执行确认 |
| 2 | 在当前 GUI 直接插入一行 | 使用紧凑历史行并统一重排垂直布局 | 低高度窗口溢出风险 |
| 3 | 从最终 Lodestone 坐标判断 | 从原始 `Vec3d` 命中坐标判断 | 避免取整边界偏差 |

### 最终改动

**客户端**

- [ ] 新增版本化 JSON 历史存储，最近 8 项、MRU 去重、非法项过滤和失败容错。
- [ ] 扫描 Payload 发送后记录历史。
- [ ] 配置页新增横向图标行、提示与当前目标回填，重排紧凑布局。

**服务端**

- [ ] 将共享半径上限改为 256。
- [ ] 用原始 `SearchResult.target()` 和玩家 Y 按 ±2 分类，成功提示追加本地化方向。
- [ ] 保持 loaded-only 和玩家 Inventory 排除约束。

**调研产出**

- [ ] 基于官方 Yarn/Fabric API 文档记录现状、数量级与分阶段优化建议。
